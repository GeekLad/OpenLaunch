# Plan 03-04: Server-Side Validation Route

## Objective

Create a new API route `POST /api/tokens/validate` that receives all launch parameters, runs SDK-specific constraint validation (fee rates, market caps, durations, holdback bounds), and returns structured errors before any on-chain work begins.

## Background

The frontend has Zod validation (client-side), but VALID-02 requires server-side enforcement of SDK-specific constraints that only the Meteora SDK knows (e.g., `validatePoolFees`, `getFeeTimeSchedulerParams` internal bounds). This prevents invalid parameter combinations from reaching on-chain transactions.

Key SDK constraints from RESEARCH.md:
- `MIN_FEE_BPS = 1` (minimum fee in basis points)
- `MAX_FEE_BPS_V1 = 9900` (maximum fee for v1 pools, ~99%)
- `validatePoolFees(poolFees, collectFeeMode, activationType)` — top-level validator
- Fee scheduler constructors throw if parameters are invalid

Meteora SDK v1.4.3 exports:
- `validatePoolFees`
- `getFeeTimeSchedulerParams`
- `getFeeMarketCapSchedulerParams`
- `CollectFeeMode.BothToken`, `CollectFeeMode.OnlyB`
- `BaseFeeMode.FeeTimeSchedulerExponential`, `BaseFeeMode.FeeMarketCapSchedulerLinear`

### Task 1: Create server-side fee validator module

```xml
<task>
  <id>03-04-01</id>
  <description>Create lib/validation/feeValidation.ts with SDK constraint checking functions</description>
  <read_first>
    - node_modules/@meteora-ag/cp-amm-sdk/dist/index.d.ts (validatePoolFees, getFeeTimeSchedulerParams, getFeeMarketCapSchedulerParams, MIN_FEE_BPS, MAX_FEE_BPS_V1, CollectFeeMode, BaseFeeMode)
    - lib/solana/poolUtils.ts (how SDK is currently imported and used)
  </read_first>
  <action>
    Create `lib/validation/feeValidation.ts` with:
    
    1. Export `validateLaunchParams(params: TokenFormData): { valid: boolean; errors: Record<string, string> }`
    
    2. Validation rules (in order of execution):
       - holdbackPercentage: 0 ≤ value ≤ 100 (basic bounds)
       - feeStartRate, feeEndRate, feeFixedRate: 1 ≤ value ≤ 9900 (MIN_FEE_BPS to MAX_FEE_BPS_V1)
       - startingMarketCap, endingMarketCap: > 0
       - endingMarketCap > startingMarketCap
       - feeDurationHours: > 0
       - quoteTokenMint: must be either SOL mint or USDC mint address
    
    3. SDK constructor validation:
       - If feeSchedulerMode === 'time-based':
         - Call `getFeeTimeSchedulerParams(startRate, endRate, BaseFeeMode.FeeTimeSchedulerExponential, 60 /* numberOfPeriods */, feeDurationHours * 3600 /* totalDurationSeconds */)`
         - If throws, capture error.message and add to errors as { feeSchedulerConfig: error.message }
       - If feeSchedulerMode === 'market-cap-based':
         - Call `getFeeMarketCapSchedulerParams(startRate, endRate, BaseFeeMode.FeeMarketCapSchedulerLinear, 60 /* numberOfPeriods */, priceMultiple, schedulerExpirationDuration)` — note: priceMultiple and duration need calculation from market caps and total supply, or use sensible defaults per LAUN-10 deferral
         - If throws, capture error.message
       - If feeSchedulerMode === 'fixed':
         - Skip SDK constructor (fixed fee is a simple static value)
       
    4. Top-level pool fees validation:
       - Construct a `PoolFeesParams` object with the `baseFee` from the constructor above (or static for fixed mode)
       - Call `validatePoolFees(poolFees, collectFeeMode, ActivationType.Timestamp)` — where collectFeeMode maps from `feeTokenMode`:
         - feeTokenMode === 'quoteOnly' → `CollectFeeMode.OnlyB`
         - feeTokenMode === 'both' → `CollectFeeMode.BothToken`
       - If throws, capture error.message and add to errors
    
    5. Return format: `{ valid: boolean; errors: Record<string, string> }`
       - If valid === true, errors is empty object {}
       - If valid === false, errors keys match frontend field names (e.g., "holdbackPercentage", "feeStartRate", "feeSchedulerConfig")
  </action>
  <acceptance_criteria>
    - lib/validation/feeValidation.ts exists and exports validateLaunchParams
    - File compiles: `npx tsc --noEmit lib/validation/feeValidation.ts` exits 0
    - validateLaunchParams({ holdbackPercentage: 50, feeSchedulerMode: 'time-based', feeStartRate: 50, feeEndRate: 25, feeDurationHours: 1, feeTokenMode: 'quoteOnly' }) returns { valid: true, errors: {} }
    - validateLaunchParams({ holdbackPercentage: 101 }) returns { valid: false, errors: { holdbackPercentage: 'Holdback percentage must be between 0 and 100' } }
    - validateLaunchParams({ feeSchedulerMode: 'time-based', feeStartRate: 10000 }) returns { valid: false, errors: { feeStartRate: ... }} (MAX_FEE_BPS_V1 exceeded)
    - Function handles all three fee scheduler modes without throwing unhandled exceptions
    - Errors object keys use frontend field names for easy mapping
  </acceptance_criteria>
</task>

### Task 2: Create POST /api/tokens/validate route

```xml
<task>
  <id>03-04-02</id>
  <description>Create app/api/tokens/validate/route.ts — API endpoint for server-side parameter validation</description>
  <read_first>
    - app/api/tokens/create/route.ts (existing API route pattern)
    - lib/validation/feeValidation.ts (validateLaunchParams function)
    - types/token.ts (TokenFormData shape)
  </read_first>
  <action>
    Create `app/api/tokens/validate/route.ts`:
    
    ```typescript
    import { NextRequest, NextResponse } from 'next/server';
    import { validateLaunchParams } from '@/lib/validation/feeValidation';
    
    export async function POST(request: NextRequest) {
      try {
        const body = await request.json();
        const result = validateLaunchParams(body);
        
        if (result.valid) {
          return NextResponse.json({ valid: true });
        } else {
          return NextResponse.json({ 
            valid: false, 
            errors: result.errors 
          }, { status: 400 });
        }
      } catch (error) {
        console.error('[API] Validation error:', error);
        return NextResponse.json({ 
          valid: false, 
          error: 'Internal validation error',
          details: error instanceof Error ? error.message : String(error)
        }, { status: 500 });
      }
    }
    ```
    
    Error response shape matches frontend Zod error structure:
    ```json
    {
      "valid": false,
      "errors": {
        "holdbackPercentage": "Holdback percentage must be between 0 and 100",
        "feeStartRate": "Fee rate exceeds maximum allowed (9900 bps)"
      }
    }
    ```
  </action>
  <acceptance_criteria>
    - app/api/tokens/validate/route.ts exists with POST handler
    - File compiles and lint passes
    - POST /api/tokens/validate with valid params returns 200 { valid: true }
    - POST /api/tokens/validate with holdback >100 returns 400 { valid: false, errors: { holdbackPercentage: "..." } }
    - POST /api/tokens/validate with fee rate >9900 returns 400 { valid: false, errors: { feeStartRate: "..." } }
    - Error responses include structured errors object with field-level messages
    - Server logs include [API] Validation error prefix on exceptions
    - Route follows same pattern as app/api/tokens/create/route.ts (import conventions, error handling)
  </acceptance_criteria>
</task>
```

    1. Before opening the confirmation modal (or before calling the actual onSubmit if modal is skipped), call:
       ```typescript
       const response = await fetch('/api/tokens/validate', {
         method: 'POST',
         headers: { 'Content-Type': 'application/json' },
         body: JSON.stringify(getValues())
       });
       const validation = await response.json();
       ```
    
    2. If validation.valid === false:
       - Map returned errors to react-hook-form field errors using `setError(field, { type: 'server', message: errors[field] })`
       - Do NOT open the confirmation modal
       - Show a generic toast/alert at top of form (optional): "Some values failed validation. Please review the highlighted fields."
    
    3. If validation.valid === true:
       - Continue to open the confirmation modal (from Plan 03-03)
    
    4. The `isLoading` state should include the validation API call (setIsLoading(true) before fetch, false after).
    
    Important: This is an additional gate AFTER client-side Zod validation but BEFORE the modal. The modal only opens if BOTH client-side AND server-side validation pass.
  </action>
  <acceptance_criteria>

## Verification Criteria

- [ ] validateLaunchParams correctly validates all parameter combinations
- [ ] API route returns structured 400 errors for invalid params, 200 for valid
- [ ] Frontend calls API before modal, displays returned errors inline
- [ ] Two-layer validation: Zod (client) → API (server) → modal → submit
- [ ] All tasks compile and pass `npm run lint`

## must_haves

1. Server-side validation MUST include SDK constructor calls (`getFeeTimeSchedulerParams`, `getFeeMarketCapSchedulerParams`) that throw on invalid params — these are the "ground truth" validators.
2. Error response keys MUST match frontend field names for seamless `setError()` mapping.
3. Validation MUST be a blocking gate — the modal MUST NOT open if server validation fails.
4. Frontend Zod schema MUST also enforce the same bounds so users get immediate feedback before API call.
