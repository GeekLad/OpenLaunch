# Plan 04-03: Add Pre-flight Validation and Error Handling

## Objective

Replace the skipped pre-flight transaction simulation (infeasible because pool tx references a not-yet-created mint) with strengthened server-side validation that runs before any transactions are built. Validation failures produce structured field-level errors and hard-stop the launch flow.

---

## Tasks

### Task 1: Create `lib/validation/launch.ts` with comprehensive parameter validation

**`<read_first>`**
- `.planning/phases/04-blockchain-integration-pre-flight-safety/04-CONTEXT.md` (D-16 through D-19)
- `.planning/phases/04-blockchain-integration-pre-flight-safety/04-RESEARCH.md` (Section 5.2: Strengthened Server-Side Validation)
- `types/token.ts` (`TokenFormData` shape)
- `config/defaults.ts` (default values for bounds)
- `lib/db/schema/tokens.ts` (column types and constraints — match server-side checks to DB limits)

**`<action>`**
1. Create `lib/validation/launch.ts` exporting:
   - `interface LaunchValidationError { field: string; message: string; code: string; }`
   - `function validateLaunchParams(formData: TokenFormData): LaunchValidationError[]`
2. Implement checks in this order (hard-stop on first violating check is NOT required — collect all errors):
   - **Supply:** `totalSupply > 0`, integer, `≤ Number.MAX_SAFE_INTEGER`
   - **Holdback:** `0 ≤ holdbackPercentage ≤ 100`
   - **Price range:** `priceRangeMin > 0`, `initialPrice > priceRangeMin`, `priceRangeMax > initialPrice`
   - **Fee rates:** `startRate, endRate, baseFeeBps ≥ 0` and `≤ 10000` (0–100% in bps)
   - **Market cap:** `startingMarketCap > 0`, `endingMarketCap > startingMarketCap` (only when fee mode is market-cap-based)
   - **Duration:** `durationMinutes > 0` (only when fee mode is time-based)
   - **Quote token:** `quoteTokenMint` must be a valid Solana pubkey (use `PublicKey.isOnCurve` or regex) and must match a known mint (SOL or USDC)
   - **Number of periods:** `feeDecayPeriods > 0` and `≤ 1000`
3. Return an empty array `[]` when all checks pass.
4. Export a helper `isValidSolanaAddress(address: string): boolean` for reuse.

**`<acceptance_criteria>`**
- `lib/validation/launch.ts` exists and exports `validateLaunchParams` and `LaunchValidationError`
- `validateLaunchParams({ ...mockFormData, holdbackPercentage: 101 })` returns an error with `field === 'holdbackPercentage'`
- `validateLaunchParams({ ...mockFormData, quoteTokenMint: 'invalid' })` returns an error with `field === 'quoteTokenMint'`
- `validateLaunchParams(mockValidFormData)` returns `[]`
- `npm run lint` passes

### Task 2: Integrate validation into `launchService.ts` and propagate errors

**`<read_first>`**
- `lib/services/launchService.ts` (top of `launchToken` method, lines 39–50)
- `lib/validation/launch.ts` (the function created in Task 1)
- `components/forms/TokenLaunchForm.tsx` (verify how `launchService.launchToken` errors are surfaced in UI)

**`<action>`**
1. At the very top of `launchToken` (before Step 1 / before line 46), add:
   ```typescript
   const validationErrors = validateLaunchParams(formData);
   if (validationErrors.length > 0) {
     throw new ValidationError('Launch parameter validation failed', validationErrors);
   }
   ```
2. Create a `ValidationError` class in `lib/validation/launch.ts` extending `Error` with an `errors: LaunchValidationError[]` property:
   ```typescript
   export class ValidationError extends Error {
     constructor(message: string, public errors: LaunchValidationError[]) {
       super(message);
       this.name = 'ValidationError';
     }
   }
   ```
3. In `lib/services/launchService.ts`, import `validateLaunchParams` and `ValidationError` from `@/lib/validation/launch`.
4. Verify the existing catch block (lines 517–526) already calls `this.updateStatus({ step: "error", ... })` and re-throws. Ensure `ValidationError` instances are caught and their `errors` array is preserved in the thrown error (e.g., by using `error instanceof ValidationError` in the caller).
5. In the API route `app/api/tokens/create/route.ts`, verify it already accepts all new fields (holdbackPercentage, quoteTokenMint, feeSchedulerMode, feeTokenMode, etc.) — it should based on Phase 1 work, but confirm no fields are missing.

- Validation returns ALL errors, not just the first one
- A validation failure prevents transaction building entirely (hard stop)
- `ValidationError` preserves the structured error array for UI display
- API route accepts and persists all configurable parameters to the database
